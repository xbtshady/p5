## 一、视觉定位

**界面以中性灰为主，照片是全站唯一有颜色的东西。**

这是 0.6 定的方向（原话：好看一点的现代感 —— 灰 + 白 + 透明磨砂）。它不改变任何产品形态，
只决定界面用什么颜色、用什么质感。

产品定位与「不做 Dashboard」这类判断以 [PRODUCT-1.0.md](PRODUCT-1.0.md) 为准，
本文档不重复、不引申。视觉上只承接其中两条已有约束：

| 产品文档里的约束 | 落实为视觉规则 |
|------------------|----------------|
| 照片是主体（大图、少文字） | 界面取中性灰，不给照片染色调（§2.1） |
| 首页是照片流，不是 Dashboard | 不做统计块、不做图表卡（§7.1） |

## 二、三条底层原则

### 2.1 照片是主角，界面是相框

照片来自任何地方，颜色不可控。所以界面只能取**中性色**——不带暖黄、不带冷蓝、不带任何倾向的灰阶。

推论（都踩过）：

- 不能给卡片配彩色描边或彩色底色，会和照片里的颜色打架
- 照片上的浮层控件（如删除按钮）**不能用白色圆底** —— 浅色照片上会直接消失，必须用**半透明深底 + 白色图标**
- 主色只能出现在两个地方：**全屏按钮**（登录 / 保存）和**焦点圈**。别的地方一律不出现

### 2.2 层次靠「浮起」，不靠「描边」

淡色底上的 1px 灰边框既显脏，又会和照片抢线条。所有层次用**阴影 + 玻璃**表达，不用边框。

两级阴影（`--shadow-1/2`）表达「卡片」与「卡片被拿起」；第三级 `--shadow-3`（更大更散）专门给玻璃卡片——磨砂表面本身没有边界感，必须靠外扩的阴影把自己从背景上托起来。

**例外**：表单里的输入控件需要清楚的轮廓（否则看不出哪里能点），那里可以用描边。

### 2.3 全站只有两级文字色

`--text`（正文）和 `--muted`（次要）。层级靠**字号**（15 / 13 / 12px）区分，不靠第三级浅灰。

原因：满足 WCAG 的第三级灰（约 `#9a9fa8`）对比度只有 2.46:1，白底上读不清。为了让「层级更清晰」而引入一个读不清的颜色，是拿可用性换视觉效果，不划算。

## 三、配色系统

### 3.1 一个来源

所有颜色定义在 `css/style.css` 的 `:root`，**改主题只改这一处**。Vant 的语义色也全部指回这些变量，所以全站（含组件库）配色只有一个来源。

```css
--bg: #eceef1;          /* 页面底：冷灰 */
--card: #ffffff;        /* 卡面（实色，用于降级） */
--card-solid: #ffffff;
--skeleton: #e4e6ea;    /* 图片未解码时的占位灰 */
--text: #16181c;        /* 正文 */
--muted: #6c717b;       /* 次要文字 */
--accent: #16181c;      /* 主色：近黑 */
--accent-ink: #2b2f36;  /* 主色按下态 */
--danger: #d8452f;      /* 破坏性动作、错误文字 */
--border: rgba(22, 24, 28, 0.08);
--border-strong: rgba(22, 24, 28, 0.16);
```

### 3.2 为什么是「冷灰 + 近黑」而不是「暖白 + 墨绿」

0.1–0.5 用的是暖白底（`#f7f6f3`）配墨绿主色（`#0a7d60`）。0.6 换掉了，两条理由：

1. **暖白会给照片加一层黄调。** 暖底色会在视觉上「污染」照片的白平衡，而看照片是这个应用的全部用途，这是致命的。冷灰（`#eceef1`）是中性偏冷的白纸观感，对照片颜色最诚实。
2. **有颜色的按钮抢注意力。** 墨绿主色在淡色界面里是除照片之外最显眼的元素；换成近黑之后，界面里唯一有颜色的东西就只剩照片了 —— 直接服务于 §2.1。

代价：主色不再有「品牌感」。这对私人项目不是问题 —— 界面本来就该隐形。

**对比度**（已按 WCAG 算过，不是估的）：

| 组合 | 用途 | 对比度 |
|------|------|--------|
| `--text` / 白卡 | 正文 | 17.6:1 |
| `--muted` / 白卡 | 次要文字 | 4.6:1 |
| 白色 / `--accent` | 按钮文字 | 17.4:1 |
| `--danger` / 白卡 | 错误提示 | 4.6:1 |

正文目标 ≥ 7:1，次要文字与按钮 ≥ 4.5:1。改配色时必须重算 —— 这个值不能靠眼睛判断。

**两级文字色 + 三级字号**是硬约束，不要在 `--text` 和 `--muted` 之间再加一档。

### 3.3 不许出现硬编码颜色

`css/style.css` 里除 `:root` 那一块之外，不允许出现十六进制色值。需要半透明黑/白时用 `rgba(22, 24, 28, α)`（与 `--text` 同源），需要浅底时用低 α 的同一支黑。

理由：全站配色只有一个来源，才能做到「改主题只改一处」。一旦某处硬编码，换主题时它就会成为留在旧配色里的一颗钉子。

**检查方法**（改完样式跑一次）：

```bash
grep -n -E "#[0-9a-fA-F]{3,8}|rgba?\(" css/style.css | grep -v "^1[0-9]:\|:root"
```

输出应该只有 `:root` 内部和少数几处刻意保留的 `rgba` 光斑定义。

## 四、磨砂（Glassmorphism）

### 4.1 使用范围

只有三处，**不要扩大**：登录卡 `.card`、列表照片卡 `.shot`、顶栏 `.topbar`。

系统弹窗（Vant 的确认框 / 图片预览遮罩）不参与 —— 弹窗需要绝对的可读性，模糊背后内容弊大于利。

### 4.2 关键前提：背后必须有东西可透

**这是磨砂最容易做错的地方。** 毛玻璃只是模糊它背后已有的内容 —— 如果背后是一片纯色灰，模糊完还是纯色灰，肉眼看不出任何区别。

所以 `body::before` 铺了一层固定的背景光斑（三个低饱和中性圆斑 + 一层纵向渐变）。**磨砂效果有一半靠这层底。**

```css
body::before {
  content: "";
  position: fixed;      /* 固定画布，不跟着内容滚 */
  inset: 0;
  z-index: -1;
  background-image:
    radial-gradient(520px 420px at 12% 8%, rgba(255,255,255,0.9), transparent 62%),
    radial-gradient(460px 460px at 88% 22%, rgba(198,205,216,0.55), transparent 64%),
    radial-gradient(560px 480px at 50% 104%, rgba(176,184,197,0.42), transparent 66%),
    linear-gradient(180deg, #f2f3f6 0%, var(--bg) 46%);
}
```

注意这层挂在 **`html` 的伪元素上而不是 `body`**：列表页的 `body` 是跟随内容增长的有高度块，挂上去背景会跟着滚，顶部露出空白。

### 4.3 参数

| 变量 | 值 | 用途 |
|------|-----|------|
| `--glass` | `rgba(255,255,255,0.72)` | 卡片 |
| `--glass-strong` | `rgba(255,255,255,0.86)` | 顶栏（上面有文字要读，更实） |
| `--blur` | `18px` | 模糊半径 |

卡片（0.72）比顶栏（0.86）透，因为卡片上的文字有 `.shot-body` 那层半透明白底托着，顶栏没有东西可以托。

### 4.4 必须配降级

不支持 `backdrop-filter` 的浏览器上，`rgba(255,255,255,0.72)` **仍然生效** —— 结果是一张半透明卡压在光斑上，没有模糊，字会看不清。

所以文件末尾有一块 `@supports not`，把「玻璃」退回「实色」。它只在这类浏览器里命中，现代浏览器一行都不执行：

```css
@supports not ((backdrop-filter: blur(1px)) or (-webkit-backdrop-filter: blur(1px))) {
  .card, .shot { background: var(--card-solid); border-color: var(--border); }
  .topbar { background: var(--bg); }
  .shot-body { background: transparent; }
}
```

### 4.5 磨砂卡的边界

磨砂表面没有明确轮廓，所以：

- 描边用**半透明白**（`rgba(255,255,255,0.6)`）而不是灰 —— 在玻璃边缘勾一道高光，符合真实玻璃的观感
- 阴影必须用 `--shadow-3`（大而散），不能用 `--shadow-1`，否则卡片会「浮」不起来
- 卡片**必须有足够圆角**（16–24px）。小圆角的磨砂块看起来像半成品

## 五、布局与间距

### 5.1 两套页面壳

| 壳 | 用在 | 结构 |
|----|------|------|
| `.card` 单卡片 | 登录页 | `body` 是 flex 居中容器，页面就是一张卡 |
| `.page-list` 顶栏 + 内容 | 照片流、新增页 | 顶栏 sticky 在顶，内容从下往上排 |

两套壳的差别写在 `body` 的类上，不要在页面里各写一套。

### 5.2 顶栏是 sticky 的，内容区必须自己躲开

顶栏 `position: sticky` 会盖住内容区开头，所以 `.feed-wrap` 的 `padding-top` 要补上「顶栏高度 + 安全区」：

```css
padding-top: calc(61px + env(safe-area-inset-top, 0px));
```

**61px 这个数字不要手算。** 它等于顶栏的 `padding(14+14)` + 内容高度（约 30px）+ `border(1px)`，见 §5.4 的核对方法。

漏了这一步的症状：列表第一张照片被顶栏盖掉上沿，看起来像「卡片跑上去了」。

### 5.3 安全区

有刘海的机器上，横放时左右要留位：

```css
padding-right: max(20px, env(safe-area-inset-right, 0px));
padding-left: max(20px, env(safe-area-inset-left, 0px));
```

`viewport-fit=cover` 已经写在三个 HTML 的 `<meta viewport>` 里了。

### 5.4 改完布局必须核对

不要靠感觉，用无头 Chrome 量。三个宽度（320 / 360 / 430）+ 以下指标：

| 指标 | 期望 |
|------|------|
| `scrollWidth - innerWidth` | `0`（无横向溢出） |
| 顶栏高度 | 和 `padding-top` 里的 61 对得上 |
| 照片卡的下沿 | 不被顶栏覆盖 |
| 删除按钮位置 | 在卡片内部（`delInside=true`） |

**无头 Chrome 的坑**：`--window-size` 对 `--headless=new` 的页面宽度无效（恒为 500px 左右）。要测真窄屏，把被测页套进一个宽度可控的 `<iframe>`，并且注意 `--dump-dom` **只导顶层文档、不进 iframe** —— 让 iframe 里的脚本把结果写到父页面的 `document.title` 上，再从命令行 grep。

## 六、动效

只有三条，都必须是「**入场**」性质的 —— 只在元素出现时跑一次，不循环、不呼吸、不闪烁。

| 关键帧 | 用在哪 | 效果 |
|--------|--------|------|
| `rise` | 卡片入场 | 从下方 8px 浮上来 + 淡入 |
| `develop` | 图片解码完成 | 从 0.35 透明度「显影」 |

时长 120–240ms，曲线 `--ease` / `--ease-io`。

规则：

- **触屏上不绑 hover 效果**（外面套 `@media (hover: hover)`）—— 手机上 hover 会「粘住」不消失，卡片一直浮着
- `transition` 只写具体属性（`box-shadow` / `transform`），不写 `all`
- 图片的 `develop` 从 0.35 而不是 0 开始：起点全透明会在那一帧闪出底色

### 6.1 必须尊重「减少动态效果」

文件末尾那段 `prefers-reduced-motion` 把动画压到 `0.001ms` 而**不是删掉** —— `animation: none` 会让 `animation-fill-mode: both` 失效，元素停在 `rise` 的起始帧，也就是 `opacity: 0`，整页空白。压时长能保留终态。

### 6.2 错峰入场：`--i` 必须是数字

列表卡片的入场延时时 `calc(var(--i, 0) * 50ms)`（第 n 张晚 50ms，封顶 6 免得第 20 张要等 1 秒）。

**⚠️ 这个坑值得单独记一条。** 模板里传 `:style="{ '--i': 6 }"`（数字）没问题，但**传字符串 `'6'` 会让 `calc('6' * 50ms)` 变成非法表达式**，而一旦 `animation-delay` 非法，**同一规则里的 `animation` 简写会一起失效** —— 动画不跑，元素停在 `rise` 的 `from` 帧，也就是 `opacity: 0`。

症状：**卡片全透明，控制台一声不吭。** 我在这上面栽过一次（改配色时截图发现整个列表是空的）。

两道防护都留着：

1. 模板传数字（Vue 对数字不加引号；字符串会被原样写进 `style`）
2. CSS 里把 `animation-delay` **写成独立属性**，不并入 `animation` 简写 —— 最坏情况只丢延时，不丢整条动画

## 七、组件

### 7.1 UI 库用 Vant 4，但只在必要处用

选型理由见 [ARCHITECTURE.md](ARCHITECTURE.md) §1。设计上的原则是：**组件库负责控件，不负责壳。**

- 用 Vant 的：输入框（`van-field`）、上传（`van-uploader`）、全屏看图（`showImagePreview`）、确认弹窗（`showConfirmDialog`）
- 自己写的：卡片外壳、顶栏、按钮视觉、空状态

理由：Vant 的默认视觉（iOS 风、大量 16px 外边距、自带白底卡片）套不进 P5 的磨砂壳。硬套的结果是「一层玻璃上贴着一张不透明的白卡」。所以只借控件的行为，视觉交给自己。

### 7.2 Vant 的三条硬约定

改任何页面之前先记住，**三条都会静默失败**（详见 ARCHITECTURE.md §8.2）：

1. `css/style.css` 的 `<link>` 必须在 Vant `index.css` **之后**，否则 `--van-*` 覆盖被默认值盖掉
2. 页面脚本里 `app.use(vant)` 一步不能漏，漏了组件渲染不出来且不报错
3. 所有 `van-*` 写**完整闭合标签**，`<van-field />` 会吞掉后面所有同级组件

### 7.3 空状态

一行字就够，配一个虚线空相框（`.empty::before`）。

理由：目前只有一条空状态文案（「还没有照片。点右上角 ＋ 记下第一张。」），已经说清楚了。
加插画或引导按钮属于功能层面的决定，不是视觉能自己拍的，要做另开一处讨论。

### 7.4 破坏性动作

用 `--danger` 那支红，且**必须二次确认**。确认弹窗的按钮颜色和全站用的是同一支红 —— Vant 的 `confirmButtonColor` 吃的是字面量，改配色时这里要跟着改（这是全站唯一一处颜色值写在 JS 里的地方）。

## 八、可访问性

底线要求，不是加分项：

- **对比度**：正文 ≥ 7:1，次要文字与按钮 ≥ 4.5:1，改配色后重算
- **键盘可达**：所有可点元素有 `:focus-visible` 样式。照片上的浮层控件（删除按钮）的焦点圈用**白色**，因为底下可能是任意颜色的照片
- **触屏 target**：可点元素不小于 30×30px
- **图片有 `alt`**：照片用标题兜底，标题为空时用「照片」
- **`prefers-reduced-motion`**：见 §6.1

## 九、改样式的标准流程

1. **只改 `:root`** —— 要改颜色，先试着只动变量。动不了再考虑改具体规则
2. **不要硬编码颜色**（§3.3），改完跑一次那条 `grep`
3. **核对布局**：无头 Chrome 跑 320 / 360 / 430 三档，看 §5.4 那张表
4. **实际看一眼**：截图确认，不要只看 DOM 数值。我漏过「卡片全透明」就是只量了 `overflowX=0` 就以为没问题
5. **大括号配平**：`python -c "s=open('css/style.css',encoding='utf-8').read(); print(s.count('{'), s.count('}'))"`
6. **临时预览页用完就删**，`git status --short` 必须干净
